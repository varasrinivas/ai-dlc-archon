I've written `requirements.md` in the run's artifacts folder. This is the first version; there wasn't one before, so it isn't a revision.

**The rule:** a request's age is the number of business days after the day it arrived, up to and including the `asOf` date. Saturdays, Sundays and the tenant's holidays don't count. A row is flagged when its age is more than the threshold, which is 5 and comes from configuration.

**Functional requirements (FR1–FR12):**
- Each row from `GET /requests/pending` gains two fields: `ageBusinessDays` and `overFiveBusinessDays`.
- The arrival day counts as day 0. A request that arrives on a weekend or holiday simply starts counting on the next business day.
- The flag means strictly more than 5, and the 5 is a setting in `application.yml`.
- Holidays are one JSON file per tenant in the API's resources. TX-01's file holds the 11 dates for 2026 that Ravi and Meena gave.
- "Today" is the date in the server's time zone, read from a `Clock` so tests can fix it. Callers can pass `?asOf=YYYY-MM-DD` to pin the date; a badly formed date gets a 400 error.
- If `asOf` is on or before the arrival date, the age is 0, never negative.
- The API only reports the flag. It never hides, filters, reorders, refuses or alerts on a row.
- Existing fields don't change, and the version stays 1.0.2.

**Non-functional requirements (NFR1–NFR7):**
- No new dependency; the new JSON fields are added without changing existing ones.
- Tests never depend on the real date. They cover weekends, the 10-12 holiday, the 5 vs. 6 boundary, and a bad `asOf`.
- `PriorAuthRequest` and `RequestStore` stay unchanged.
- The app refuses to start if a holiday file or the threshold setting is invalid.
- `verify.sh` must pass before the change counts as done.

**Assumptions (A-01–A-08):**
- **Needs confirming (A-01):** that the nightly report really uses this rule. We can't see its code, so I suggest checking one real report row.
- **Needs confirming (A-02):** a tenant with no holiday file counts weekends only and logs a warning, rather than stopping the app.
- Only 2026 holidays are known, so ages that run into other years will be too high.
- "Server's zone" means the JVM's default time zone.
- The field names stay as they are even if the threshold changes.

Ten words

workflow
the YAML file with the team's process (request-to-pr): which steps, in which order, where to stop for people
node
one step of a workflow: an agent prompt, a bash command, a loop or a wait
run
one execution of a workflow, with a run id; it keeps a transcript, the files it wrote and what it cost
wait
a node that pauses the run until someone answers
form
what a wait accepts: message, approval, select
loop_group
a few nodes repeated until a check passes; here, until the requirements are approved
until_bash
the shell check that ends a loop on exit 0
workspace
the team's folder around the code repo: .archon/, CLAUDE.md, scripts, requests; a git repo of its own
folder project
a workspace registered with --folder: Archon runs in place, no worktree, the agent does the git
artifacts
the files a run writes for people and later nodes: scan.md, requirements.md, plan.md…
