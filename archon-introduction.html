1
why

The problem Archon solves

If you have never used an AI coding agent with a process around it: what goes wrong without one.

read · 2 min

An AI coding agent (Claude Code, Codex and the like) is a program you give a task in plain English; it reads your code, edits files and runs commands until it thinks the task is done. It is fast and often right. Left alone, though, it decides for itself what to do first, what to ask, and when it's finished. On a team, that's the part that goes wrong:

An agent on its ownThe same agent, run by Archon
Order of workwhatever the agent picks this timethe order the team wrote down: read the code, ask, write requirements, plan, build, review
Questionsit guesses an answer and carries ona step that writes the questions down and stops until a person answers
Sign-offnobody, unless someone happens to looknamed people approve the requirements, the plan and the change before it is pushed
“Done”the agent says soa check you chose passes (here: the project's tests, through scripts/verify.sh)
Afterwardsa chat history, if you kept ita transcript, every file each step wrote, and the cost, per run
Next timea different path againthe same steps, because they are in a file in the team's repo
In plain words. Archon doesn't write code. It's the checklist and the traffic lights around the agent that does: it tells the agent which step is next, and turns red where a person has to look.
When it isn't worth it: a one-off, two-line edit you'd review in ten seconds anyway, or if you don't use a coding agent yet. Archon pays off when the same kind of work comes round again and more than one person has a say in it.

One request, start to finish

What the course actually did with Archon, in plain words. Every line is from the real run.

read · 3 min
  1. The request. Ravi, a nurse manager, asks in Slack for the list of pending requests to show how many business days each has been waiting, and flag those over 5. Kiran, a developer, saves it as docs-in/request.md and starts the team's workflow with one command.
  2. Read, then ask. The agent reads the code and writes down 7 questions only people can answer (where do the holidays come from? which date is 201ctoday201d? what are the field names?). The run stops. Kiran types the team's answers.
  3. Requirements, rejected once. The agent writes the requirements. Meena, the tech lead, rejects the first draft: the screen team already chose other field names. The agent revises; she approves the second.
  4. Plan. The agent writes a plan: which files, which tests, which branch. Meena approves it.
  5. Build until the tests pass. The agent writes the code and runs the tests; it would loop until they pass. They passed on the first try.
  6. Review. A second agent, which can read but not change anything, reviews the change: READY.
  7. A person catches what the agents missed. Before approving, Kiran tries the built program by hand. One silly date (the year 999,999,999) makes it crash with a 500 error. Meena rejects the change, which ends the run.
  8. Fix. Kiran starts a small follow-up workflow on the same branch. The agent makes the bad date a clean error (400) instead, and all 21 tests pass. Kiran re-checks by hand and pushes.
  9. Merge. Meena merges the branch; the tests pass on main. Ravi's screen can show the age.

4
the idea

What Archon is, in four sentences

Now the same thing in Archon's terms, so the rest of the page has somewhere to land.

read · 2 min

In one sentence: you describe, in a file, how your team does a kind of job; Archon makes the AI agent do it in that order and stops wherever a person has to decide.

Archon is an open-source workflow engine for AI coding. The file is a YAML workflow, and Archon runs it the same way every time. A workflow is a graph of nodes (steps): an AI node hands a prompt to the agent you already use (Claude Code, Codex or Pi), a code node runs a command, and a wait node stops until a person answers.

A run works either in place in a workspace that holds your repos (a folder project, what this course uses) or in its own git worktree and branch (a repo project), and keeps a transcript, the files each node wrote and what it cost. Archon 0.13.2 (29 Oct 2026) ships 25 workflows of its own, the sdlc pack, and you add yours in a .archon/ folder.

The kinds of node, and which of them cost money (an AI model bills by the token, roughly ¾ of a word read or written; a command or a pause costs nothing):

Node bodyWhat it doesCosts model tokens?
prompt: / command:Sends an inline prompt, or a Markdown command file, to the agentyes
loop: / loop_group:Repeats an agent step (or a small graph) until a check passesyes
bash: / script:Runs a shell script, or TypeScript (bun) / Python (uv)no
wait:Pauses for a time, an event, or a person's answerno
cancel:Ends the run with a reasonno
include: / workflow:Reuses another workflow, inlined or as a child rundepends
In plain words. A coding agent on its own is a talented cook who improvises. Archon is the recipe card on the wall: the cook still cooks, but in the order the card says, and the chef tastes before anything leaves the kitchen.

Not the old Archon: until 2025 the name meant a knowledge-base and task MCP server (kept on the repo's archive/v1-task-management-rag branch). Everything here is the workflow engine.

the idea

How one node runs

Every workflow is built from this one move: a node gets inputs, does one job, and hands its output on.

read · 2 min
The agent in an AI node is a full Claude Code session in the run's folder (the workspace in this course, or a run's worktree): it reads files, runs commands and edits code, and it reads the CLAUDE.md there. What it may do is set by the node (allowed_tools, denied_tools, mutates_checkout: false), not by Archon guessing.

What Archon hands to Claude Code

How each part of the YAML turns into Claude Code's own pieces: sessions, prompts, skills, subagents, hooks, MCP.

read · 4 min
In plain words. Archon doesn't type into your Claude Code. Its Claude provider uses the Claude Agent SDK, which starts Claude Code as a background process. Each AI node becomes one Claude Code session in the run's folder, with your claude.ai login, and the node's fields decide what that session gets. Everything else (the order, the loops, the checks, the waits) is Archon's and never reaches Claude.

What you type at each pause

A wait node stops the run and puts it in the attention queue. The form it declares says what it accepts.

reference
FormYou answer withThe next node reads

Archon returns real · printed under every pause in the course run
Approve: `archon workflow approve d9d9f6523154ac4773648b9a08d84989 [text]`
Reject: `archon workflow reject d9d9f6523154ac4773648b9a08d84989 [text]`
Abandon: `archon workflow abandon d9d9f6523154ac4773648b9a08d84989`
Workflow paused — waiting for approval.
In plain words. A pause is the workflow asking a person a question. You see it in archon workflow attention, and you reply with one command: approve, reject or answer, followed by your text. The agent reads your text in the next step.
In plain words. Reject is an answer, not a stop. The run carries on with decision reject; the workflow decides what that means. In request-to-pr, a rejected requirements draft is revised (the loop_group), a rejected plan or change goes to a cancel: node.
Answering from the CLI continues the run in that terminal until the next pause or the end. Add --json to record the answer and return at once; archon serve or archon workflow wake then continues it.

In plain words. You only need two flags at first: --folder on your first run in a workspace, and --detach to get your terminal back while it works. The rest is here for when you need it.
The course starts its run from the workspace root with archon workflow run request-to-pr --folder --detach "Implement the request in docs-in/request.md": --folder registers the workspace as a folder project the first time, and --detach runs it in the background (so the terminal is free while it works). In a repo project you would name the branch with --branch instead; a folder project rejects it.

Archon words

workflow
the YAML file with the team's process (request-to-pr): which steps, in which order, where to stop for people
node
one step of a workflow: an agent prompt, a bash command, a loop or a wait
run
one execution of a workflow, with a run id; it keeps a transcript, the files it wrote and what it cost
wait
a node that pauses the run until someone answers
form
what a wait accepts: message, approval, select
loop_group
a few nodes repeated until a check passes; here, until the requirements are approved
until_bash
the shell check that ends a loop on exit 0
artifacts
the files a run writes for people and later nodes: scan.md, requirements.md, plan.md…
workspace
the team's folder around the code repo: .archon/, CLAUDE.md, scripts, requests; a git repo of its own
folder project
a workspace registered with --folder: Archon runs in place, no worktree, the agent does the git
worktree
a second checkout of a repo in another folder, on its own branch; Archon makes one per run in a repo project
provider
the coding agent Archon drives: Claude Code here (Codex and Pi are the others)
token
the unit an AI model counts and bills text in, roughly ¾ of a word; agent nodes use them, bash and waits don't
