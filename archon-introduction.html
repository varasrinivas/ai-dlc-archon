Meet Archonsteps 1–4 · the idea, one node, one workflow, the people
1
the idea

What Archon is, in four sentences

Before any command: what kind of tool this is, so the rest of the page has somewhere to land.

read · 2 min

Archon is an open-source workflow engine for AI coding: you write how a kind of work gets done as a YAML workflow, and Archon runs it the same way every time. A workflow is a graph of nodes; an AI node hands a prompt to the agent you already use (Claude Code, Codex or Pi), a code node runs a command, and a wait node stops until a person answers. Each run works in its own git worktree and branch, and keeps a transcript, the files each node wrote and what it cost. Archon 0.13.2 (29 Oct 2026) ships 25 workflows of its own, the sdlc pack, and you add yours in the repo's .archon/ folder.

Node bodyWhat it doesCosts model tokens?
prompt: / command:Sends an inline prompt, or a Markdown command file, to the agentyes
loop: / loop_group:Repeats an agent step (or a small graph) until a check passesyes
bash: / script:Runs a shell script, or TypeScript (bun) / Python (uv)no
wait:Pauses for a time, an event, or a person's answerno
cancel:Ends the run with a reasonno
include: / workflow:Reuses another workflow, inlined or as a child rundepends
In plain words. A coding agent on its own is a talented cook who improvises. Archon is the recipe card on the wall: the cook still cooks, but in the order the card says, and the chef tastes before anything leaves the kitchen.

Not the old Archon: until 2025 the name meant a knowledge-base and task MCP server (kept on the repo's archive/v1-task-management-rag branch). Everything here is the workflow engine.

the idea

How one node runs

Every workflow is built from this one move: a node gets inputs, does one job, and hands its output on.

read · 2 min
The agent in an AI node is a full Claude Code session in the run's worktree: it reads files, runs commands and edits code, and it reads the repo's CLAUDE.md. What it may do is set by the node (allowed_tools, denied_tools, mutates_checkout: false), not by Archon guessing.

Archon does not give one run a worktree in each of two repos. The docs' advice: keep the root as a folder project for cross-repo work, and let each repo also be its own project (run from inside it) for a change that touches only that repo. Workflows can also live outside every repo: ~/.archon/workflows/ appear in all your projects (yours, not the team's), and --workflow-source <dir> reads the workflow from one folder and runs it against --cwd. A wait node stops the run and puts it in the attention queue. The form it declares says what it accepts.

Workflow paused — waiting for approval.
In plain words. Reject is an answer, not a stop. The run carries on with decision reject; the workflow decides what that means. In request-to-pr, a rejected requirements draft is revised (the loop_group), a rejected plan or change goes to a cancel: node.
Answering from the CLI continues the run in that terminal until the next pause or the end. Add --json to record the answer and return at once; archon serve or archon workflow wake then continues it.
