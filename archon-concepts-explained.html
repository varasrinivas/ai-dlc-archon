The big idea, in one paragraph

Archon turns how your team works into a file. A workflow is a YAML graph of steps: some are an AI agent with a prompt, some are plain code, some are a pause where a person decides. Archon runs that graph the same way every time, each run from the team's workspace, in place, with the agent branching in each repo, checks the agent's work with commands instead of taking its word, and keeps a transcript, the files each step wrote and the cost of every run. It brings no model: it drives the agent you already use (Claude Code, Codex or Pi). The docs put the split in six words: YAML coordinates, code computes, agents judge.

In everyday termsA restaurant kitchen with a recipe card for every dish. The cooks (agents) bring the skill; the card fixes the order, the timer (a check) says when the bread is done, and the chef (you) tastes before anything leaves the pass.

Fourteen concepts follow. Each: what it is, why Archon has it, how it shows up in the tool, an example from the course's real run (Kiran's request-to-pr run on priorauth-api), an analogy, a one-line test that you have understood it, and what not to confuse it with. Facts are from Archon 0.13.2 and its docs.

Archon in one picture

Workflow

What it is

A YAML file that writes down how one kind of work gets done: its steps (nodes), the order between them, the checks that decide when a step is finished and the places where a person must decide. It needs a name, a description and nodes.

Why Archon has it

A coding agent asked to "fix this" does what it likes on that run: it may skip the plan or the tests. Archon moves the process out of the model's head into a file the team owns and reviews, so every run follows the same steps.

How it works in the tool
  • Lives in the project at .archon/workflows/<pack>/<workflow>/<name>.yaml (the team workspace in this course, or a repo; flat .archon/workflows/foo.yaml still works), or in ~/.archon/workflows/ for every project on your machine.
  • 25 workflows ship inside Archon 0.13.2 (the sdlc pack). A repo workflow with the same name overrides a home one, and a home one overrides a bundled one.
  • archon workflow list shows what it finds; archon validate workflows checks the file; archon workflow run <name> "message" starts it. Since 0.13.1 the name must match exactly.
Example from the course run

The team's request-to-pr workflow: scan, ask, write requirements until approved, plan, approve, implement until ./scripts/verify.sh passes, review, approve, push. Kiran ran it with the message Implement the request in docs-in/request.md.

In everyday termsA recipe card pinned in a restaurant kitchen. Every cook follows the same card; the cook's skill goes into each step, but nobody skips the step where the chef tastes the sauce.
You've got it when you can say which file holds your team's process, and that changing the process is a pull request on that file.

Don't confuse with: a run (one execution of a workflow) or a command (one prompt file a node uses).

Nodes: one job each

What it is

A node is one step of a workflow. Each node has an id and exactly one body: prompt or command (an AI agent), bash or script (code, no AI), loop or loop_group (repeat until a check passes), wait (pause), cancel (end the run), include or workflow (reuse another workflow).

Why Archon has it

The docs' rule of thumb is YAML coordinates, code computes, agents judge. Splitting the work into nodes lets the cheap, certain steps (run the tests, push) be code, and keeps the agent for the steps that need judgment.

How it works in the tool
  • An AI node's output is its final reply, readable later as $id.output. With output_format (a JSON Schema) the reply must be JSON, and later nodes read fields such as $plan.output.summary. A reply that doesn't fit the schema fails the node.
  • A bash node's stdout is its output. It runs under bash on every OS (Git Bash on Windows).
  • mutates_checkout: false asserts a node changes no file in the checkout; the engine compares git status before and after and fails the node if it did.
  • approval: is deprecated; use wait: with form: approval.
Example from the course run

In request-to-pr: scan is a command node, questions, plan and review are prompt nodes with output_format, checks and push are bash nodes, implement is a loop and answer, approve-plan and approve-change are waits.

In everyday termsA production line: some stations are people with skill (the agent), some are machines that always do the same thing (bash), some are an inspector's desk where the line stops until someone signs (wait).
You've got it when you can look at a step and say whether it should be an agent, a script or a pause, and why.

Don't confuse with: a Claude Code subagent. A node starts its own agent session (or none, for bash); what that agent does inside is up to it.

The graph: depends_on, when, trigger_rule

What it is

Nodes form a directed graph. depends_on lists the nodes that must finish first; nodes with no dependency between them run in parallel. when: skips a node unless a condition on earlier output holds. trigger_rule says how a node with several parents joins (default all_success).

Why Archon has it

A graph says exactly what may happen in parallel and what must wait, and conditions let one file hold several paths (approved, rejected) without a script deciding at run time.

How it works in the tool
  • A node starts when every parent has settled and its when: and trigger_rule allow it. A skipped node passes "skipped" to its children.
  • Conditions read outputs: when: "$approve-plan.output.decision == 'approve'".
  • archon workflow run <name> --dry-run walks the graph with stub outputs, without a run or a model call, and stops at the first wait.
Example from the course run

approve-plan has two children: stop-plan (when the decision is reject, a cancel node) and implement (when it is approve). Exactly one runs.

In everyday termsA wiring diagram: current flows only along the wires you drew, and a switch (when) decides which branch lights up.
You've got it when you can read a workflow and say which nodes could run at the same moment.

Don't confuse with: a sequence of steps. Order comes only from depends_on; the order of nodes in the file means nothing.

Commands and packs

What it is

A command is a Markdown file of instructions that a command: node (or a loop's command:) sends to the agent. A pack is a folder of related workflows, each with its own commands/ and scripts/, shared through git or as a plugin.

Why Archon has it

Long prompts don't belong in YAML. A command file can be reviewed, diffed and reused like code, and the package boundary stops two workflows' review.md from colliding.

How it works in the tool
  • In a packaged workflow, command: scan resolves only from <pack>/<workflow>/commands/scan.md, with no fallback.
  • Commands see the same variables as prompts: $USER_MESSAGE, $ARTIFACTS_DIR, $BASE_BRANCH, $<node>.output, $LOOP_PREV_OUTPUT in loops.
  • archon validate commands checks them; archon plugin copy <id> copies an installed pack into the repo to edit.
Example from the course run

The team's pack is team, with one workflow, request-to-pr, and two commands: scan.md (read only, write scan.md into the artifacts) and implement.md (the loop's prompt: implement the approved plan, run the verify script, commit).

In everyday termsA recipe card (workflow) that says "make the sauce, see card 12" (command). Card 12 sits in the same folder as the recipe, so another recipe's card 12 never gets mixed in.
You've got it when you can say where the text a node sends to the agent comes from, and change it without touching the YAML.

Don't confuse with: Claude Code's own slash commands in .claude/commands/. Archon's commands are read by Archon and passed to the agent as its prompt.

Loops and their completion checks

What it is

A loop node repeats one agent step; a loop_group repeats a small graph of nodes. Each needs max_iterations and at least one way to finish: until_bash (a shell check exits 0), until_field (a boolean in the step's structured output) or until (a word the agent prints; the weakest).

Why Archon has it

"Keep going until the tests pass" is the most useful thing an agent loop does, and the most dangerous if the agent decides for itself when it is done. A shell check makes the code, not the model, decide.

How it works in the tool
  • until_bash runs after each pass; exit 0 ends the loop. Reaching max_iterations fails the node.
  • fresh_context: true starts each pass in a new agent session; $LOOP_PREV_OUTPUT carries the previous pass's report.
  • A loop_group whose body ends in a wait is the way to say "revise until a person approves": the next pass reads the answer as $LOOP_PREV.<wait-id>.output.text.
Example from the course run

implement is a loop with until_bash: ./scripts/verify.sh and max_iterations: 3. requirements is a loop_group: write-requirements then review-requirements (a wait), until the decision is approve. Meena's rejection with the screen team's field names sent it round once more.

In everyday termsA driving test: you can retake it up to three times, and the examiner (the check), not you, decides when you've passed.
You've got it when you can say what ends a loop, and why until_bash beats asking the agent to print DONE.

Don't confuse with: a retry. A retry repeats a failed node the same way; a loop repeats a working step until its result is good enough.

Waits and the attention queue

What it is

A wait: node pauses the run durably: for a time, for an event, or (with attention:) until someone answers a question. The question's form fixes the answer: message (free text), approval (approve or reject, plus text), select or multi_select (declared options). Paused runs make up the attention queue.

Why Archon has it

People decide; the run shouldn't hang a terminal while they think. A paused run holds no process, survives restarts, and can be answered from the CLI, the Web UI or chat. The docs call this "human on the loop, not in it".

How it works in the tool
  • archon workflow attention lists what is waiting; archon workflow wait <run-id> blocks until a run ends or needs you.
  • archon workflow approve <run-id> "text", reject, respond <option> and answer --occurrence <id> --text answer it. Answered from the CLI, the run continues in that terminal.
  • Reject does not cancel. It is an answer like any other; the workflow must route it, for example to a cancel: node with when: "$approve.output.decision == 'reject'".
Example from the course run

The run stopped at all four waits: answer (six questions, answered by Kiran for Ravi and Meena), review-requirements (rejected once with the screen team's names, then approved), approve-plan (Meena) and approve-change.

In everyday termsA form in a manager's in-tray. The work stops at the desk, nobody has to stand there waiting, and the clerk carries on the moment it is signed.
You've got it when you can add a gate to a workflow and say what happens on reject.

Don't confuse with: an AI-DLC gate, which the tool's own engine opens at fixed stages. In Archon you place every pause yourself, and there are none unless you write them.

Runs: id, status, transcript, cost

What it is

One execution of a workflow. It has a 32-character run id, a status (running, paused, completed, failed, cancelled), a JSONL transcript of every event, and recorded token usage and cost, all in Archon's database.

Why Archon has it

Governance: you can always say what ran, what the agent was told, what it said back, who answered each pause and what it cost. A failed run can be resumed from the nodes that already completed instead of starting over.

How it works in the tool
  • archon workflow runs lists recent runs; archon workflow get <run-id> shows one (path, branch, cost, artifacts); archon workflow logs <run-id> --format text reads the transcript.
  • --detach starts a run in the background; archon workflow resume <run-id> continues a failed or paused one, replaying completed nodes (Skipped (prior_success)).
  • cancel stops a run; abandon marks it cancelled and removes its worktree but keeps the branch.
Example from the course run

Kiran's run cd54631b…: started with --detach, paused five times at its four waits (the requirements wait twice), and each answer continued it in Kiran's terminal, replaying the finished nodes first.

In everyday termsA parcel's tracking number: one id that tells you where it is, every stop it made and what it cost to send.
You've got it when you can find, from a run id alone, what the agent wrote at any node.

Don't confuse with: a conversation. A chat conversation can start runs; the run is the workflow execution with its own record.

Isolation: in place, or a worktree per run

What it is

Where a run does its work. In a folder project (a workspace that holds the repos, what this course uses) it runs in place, in your own clones, and the agent makes the branches. In a repo project (.archon/ inside the repo) each run gets its own git worktree, a second checkout on its own branch under ~/.archon/workspaces/<owner>/<repo>/worktrees/; --branch names it, --no-worktree runs in your checkout.

Why Archon has it

A worktree lets several runs change the same files at once without seeing each other, and keeps your checkout as you left it. In place is simpler and spans repos, but one run at a time per workspace, on the branches you can see. Either way, if you don't like a result, you drop the branch.

How it works in the tool
  • The worktree is cut from the base branch (worktree.baseBranch in .archon/config.yaml, else detected). Only tracked files are in it, so commit what the run needs (or list ignored files in worktree.copyFiles).
  • archon isolation list shows them; archon complete <branch> removes a worktree and its local branch (the remote branch stays); archon isolation cleanup --merged removes the merged ones.
  • Not a sandbox. A worktree separates checkouts; commands a run executes can still touch files elsewhere.
  • A folder project (see Where things live) gets no worktree: it runs in place, --branch is rejected, isolation list says No codebases registered. and archon complete finds nothing. --container is its optional isolation.
Example from the course run

The course ran from java-workspace/, a folder project: the agent made request-age/pending-age in Kiran's own priorauth-api clone and committed there, and workflow get listed the workspace itself as the worktree, (live). The fix run that adopted it was told so: folder projects run in place; adoption carries provenance and $ADOPTED_RUN_DIR access only.

In everyday termsA builder gets a copy of the plans to draw on, not the originals in the office. Several builders can draw at once; the office keeps the clean set.
You've got it when you can say where a run's edits are in each layout, and how to get rid of them.

Don't confuse with: a container. Container isolation exists for folder projects and is a separate option.

Artifacts and variables

What it is

Artifacts are files a run writes to $ARTIFACTS_DIR, a folder per run outside the repo. Variables are the placeholders Archon fills in prompts, commands and bash: $USER_MESSAGE (the run message), $ARTIFACTS_DIR, $BASE_BRANCH, $WORKFLOW_ID, $<node>.output and its fields.

Why Archon has it

Nodes hand work to each other through files, not through one long chat. A fresh agent session can read just plan.md and stay focused, and the artifacts stay for people to read after the run, without cluttering the repo.

How it works in the tool
  • Artifacts live in ~/.archon/workspaces/<project>/artifacts/runs/<run-id>/ (_folder/java-workspace in this course), never in git.
  • archon workflow artifacts <run-id> lists them; add a file name to print one.
  • Node outputs used in bash: are shell-quoted; a reply over 32,768 characters is spilled to a file and substituted as $(cat …).
Example from the course run

The run left scan.md, questions.md, requirements.md, plan.md, implementation.md and review.md. The code repo got only the code and tests; the workspace repo got nothing.

In everyday termsThe folder of working papers a surveyor leaves with the client: the house only gets the finished work, the folder explains how it was decided.
You've got it when you can say where to look for a run's requirements a month later, and why they are not in the repo.

Don't confuse with: AI-DLC's record in aidlc/, which is committed with the workspace. Archon's artifacts are per run and stay on the machine that ran it unless you copy them.

Providers, models and tiers

What it is

A provider connects Archon to an agent: Claude Code, Codex or Pi (OpenCode and Copilot are deprecated). Archon brings no model of its own; it runs the agent with your login or key. A tier (small, medium, large) names a provider and model, so a workflow can say model: large.

Why Archon has it

Teams already pay for an agent and have its project guidance (CLAUDE.md). Archon uses that agent as it is, and lets a workflow pick a cheaper model for easy steps.

How it works in the tool
  • archon provider add claude installs the provider plugin (it does not install Claude Code itself). Re-run it after each Archon upgrade.
  • The project's .archon/config.yaml assistant: sets the default; a workflow or node can override provider and model.
  • archon ai tier list shows the tiers; on this install: small = claude/haiku, medium = claude/sonnet, large = claude/opus.
  • Claude Code reads the CLAUDE.md of the folder it runs in (the workspace's, here) in every AI node, so the team's rules reach each step.
Example from the course run

assistant: claude in .archon/config.yaml; no node sets a model, so every AI node used the provider's default. The run used the machine's claude.ai login: archon doctor reported Assistant login: claude: usable.

In everyday termsA staffing agency: Archon books the work and keeps the timesheets; the people come from the agencies you already use.
You've got it when you can say which agent runs a node and where that is set.

Don't confuse with: the workflow. Swapping the provider changes who does each step, not the steps.

Claude Code under each AI node

What it is

Every prompt, command or loop pass runs as one Claude Code session. Archon's Claude provider uses the Claude Agent SDK, which starts Claude Code as a background process in the run's folder, with your login. The node's fields decide what that session gets: its prompt, tools, skills, subagents, hooks and MCP servers. bash, script and wait nodes start no session at all.

Why Archon has it

Archon doesn't rebuild the agent; it reuses Claude Code's own pieces and scopes them per node. A review node can get a review skill and no Write tool while the implement node gets the opposite, and what each node may use is written in the file the team reviews.

Where things live: the workspace, its repos, and ~/.archon

What it is

Two places. The project's .archon/ holds what the team shares and commits: workflows/, config.yaml, optionally commands/ and scripts/. Your home's ~/.archon/ holds the install: the binary, plugins, global config, archon.db, and workspaces/ with every run's logs and artifacts. In this course the project is a team workspace, as in AI-DLC: a git repo of its own with .archon/, CLAUDE.md, the check and the requests at its root, and the code repos cloned inside it. Archon calls it a folder project. The other layout puts .archon/ inside a single code repo: the repo is the project.

Why Archon has it

The process is the team's and is shared through the workspace repo; the code keeps its own repos and PRs; the runs are yours and stay on your machine.

How it works in the tool
  • ~/.archon/config.yaml holds your defaults (assistant, tiers, concurrency); the project's .archon/config.yaml holds the team's (assistant; worktree settings only matter in a repo project) and wins.
  • Credentials go in ~/.archon/.env (or the project's .archon/.env, never committed); archon setup writes them.
  • The first run with --folder from the workspace root registers it as a folder project (archon project list: folder · java-workspace · _folder/java-workspace); the first run inside a plain repo registers the repo.
  • One repo or several: clone them under the workspace, with .archon/ and CLAUDE.md at the root, and run from there (the first time with --folder). The agent works at the root, in place, and sees every repo. Archon makes no worktree, branch or PR for a folder project: the agent branches, commits and pushes in each repo, so the workflow's prompts must say so. --container adds a Docker overlay with an approval before writes reach the folders. Runs are stored in ~/.archon/workspaces/_folder/<slug>/. The course ran two: one request, one repo, and one bug fixed across two repos.
  • Archon does not give one run a worktree in each of two repos. If you want worktrees for single-repo changes, the docs' advice is to also register each repo as its own project and run from inside it.
  • Workflows can also live outside every repo: ~/.archon/workflows/ (in all your projects, not shared), or --workflow-source <dir> (read the workflow from one folder, run it against --cwd).
Example from the course run

Committed in the workspace repo java-workspace: .archon/config.yaml, the team/request-to-pr workflow and its two commands, CLAUDE.md, scripts/verify.sh, docs-in/request.md, and a .gitignore that leaves out priorauth-api/. Committed in priorauth-api: only the code, through its own PR. Not committed: everything under ~/.archon/workspaces/_folder/java-workspace/.

In everyday termsThe cookbook lives in the kitchen (the workspace), the ingredients come from the pantry (the code repos, each with its own supplier), and each cook's notebook and apron live in their locker (home).
You've got it when you can say what a new teammate clones (the workspace, then each repo inside it), and why a second repo changes nothing but one more clone.

Don't confuse with: a worktree. A workspace is a folder you keep and commit; a worktree is a per-run checkout Archon makes and removes, and only a repo project gets one. AI-DLC's workspace is the same idea as Archon's folder project.

Where you work: CLI, Web UI, chat, triggers

What it is

The same runs can be started and answered from four places: the CLI (archon …), the Web UI (archon serve, port 3090: runs, chat, settings, an experimental workflow builder), chat platforms through plugins, and triggers (schedules, GitHub events, signed webhooks).

Why Archon has it

A decision should reach whoever can make it, wherever they are, without them opening a terminal.

How it works in the tool
  • The Web UI shows each run's events, artifacts and graph, and approve/reject/resume/cancel buttons; alerts can notify the browser when a run pauses.
  • archon chat "…" talks to the orchestrator, which can pick and start a workflow from your words (it reads each workflow's description).
  • Triggers are deployment configuration, not workflow YAML.
Example from the course run

The course run used the CLI only: workflow run --detach, workflow wait, answer, reject, approve. The same pauses would have shown in the Web UI's "Needs your input" banner.

In everyday termsA shop with a counter, a website and a phone line: one stock room behind all three.
You've got it when you can answer a paused run from somewhere other than where it started.

Don't confuse with: Claude Code's interactive session. You don't type into the agent; you type into Archon, which runs the agent.

The sdlc pack: a factory of queues

What it is

The 25 bundled workflows are one pack, sdlc. archon-ship takes one issue or request to a reviewed PR: triage, then investigate or plan if needed, then delivery rounds (implement, draft PR, review, CI). Around it, queues run on their own: archon-intake triages new issues, archon-build-queue works them, archon-merge-queue merges green, reviewed PRs.

Why Archon has it

It is Archon's answer to "what does a complete process look like": every stage a separate, reusable workflow, people asked only for decisions that are theirs.

How it works in the tool
  • The pack talks to GitHub through gh (or a forge plugin): archon workflow run archon-forge-check proves it can.
  • Read-only building blocks are useful alone: archon-investigate (root cause, changes nothing), archon-plan, archon-review, archon-validate.
  • 0.12.0 removed the older archon-fix-github-issue, archon-idea-to-pr, archon-smart-pr-review and archon-assist; tutorials that name them are out of date.
Example from the course run

The course writes its own small workflow to learn the parts, then shows archon-plan on the same request for comparison. The full factory needs a GitHub repo, gh and CI, which the run doesn't have.

In everyday termsA car plant next to your home garage: the same tools, but the plant has a line that runs while you sleep.
You've got it when you can say when you'd write your own workflow and when you'd run archon-ship.

Don't confuse with: a template you must use. The pack is an example and a product; your repo's workflows sit beside it.

Common misunderstandings

"Reject stops the run."Only if the workflow says so. Reject is an answer; route it to a cancel: node, or to a revision loop.
"The worktree keeps the agent safe."It keeps your checkout clean. It is not a sandbox: commands can still reach other files.
"Archon is an AI model / agent."It is an engine that runs your agent (Claude Code, Codex, Pi) inside steps you define.
"Old tutorials' workflow names still work."0.12.0 removed archon-fix-github-issue, archon-idea-to-pr and others, and 0.13.1 made names exact.
"The run's requirements end up in the repo."Artifacts live under ~/.archon, per run. Commit them only if your workflow does.
"Archon is the knowledge-base MCP server."That was Archon v1, kept on the archive/v1-task-management-rag branch. Today's Archon is the workflow engine.
"bash: nodes need WSL on Windows."They need Git Bash. Archon looks in the usual Git locations; set ARCHON_BASH_PATH if Git is elsewhere.
"Archon's files must go into each repo."Only if you choose the repo-is-the-project layout. This course keeps them in a team workspace that holds the repos (a folder project), as AI-DLC does; ~/.archon/workflows/ and --workflow-source keep workflows out of any repo too.
"My installed Claude skills work in every node."On Claude, a node gets only the skills it names in skills:. Your CLAUDE.md, subagents and hooks do load (project and user, by default); skills don't.
"Telemetry is off by default."It is on. Set ARCHON_TELEMETRY_DISABLED=1 (or DO_NOT_TRACK=1); archon telemetry status checks.

Check yourself

Answer, then open.

1. Ravi sends a second request tomorrow. New workflow or new run?

A new run of the same workflow, with the new request as its message. The workflow only changes if the team changes the process.

2. Where does Meena read the requirements the run wrote?

In the run's artifacts: archon workflow artifacts <run-id> requirements.md, or the Web UI's run page. Not in the repo.

3. Meena rejects the code plan. What happens?

approve-plan completes with decision reject; stop-plan's when is true, so the run is cancelled. implement is skipped.

4. Who decides the implement loop is finished?

./scripts/verify.sh: exit 0 after a pass ends the loop. Three failing passes fail the node.

5. Kiran's terminal crashed while the run was paused. Is the run lost?

No. A paused run holds no process; answer it from any terminal or the Web UI with its run id.

6. Which nodes cost model tokens in request-to-pr?

The prompt, command and loop nodes. checks and push (bash) and the waits cost none.

7. Why does the workspace have a .gitignore with /priorauth-api/?

The code repo is cloned inside the workspace but has its own git, remote and PRs. The ignore keeps the workspace repo to the team's files, so a code change never shows up as a workspace change.

8. The review node should use the team's code-review skill and must not edit. What goes in the YAML?

skills: [code-review] and denied_tools: [Write, Edit] on that node, plus mutates_checkout: false so the engine checks. The skill must be installed in .claude/skills/code-review/SKILL.md (or ~/.claude/skills/).

9. Ravi's next request needs priorauth-api and the reviewer screen's UI repo. Where does the team's .archon/ go?

Where it already is: the team workspace. Clone the UI repo into it next to priorauth-api and add it to CLAUDE.md's repo map; the run starts from the same root, in place, and the agent does the git in each repo. Archon makes no worktree or PR for it.
